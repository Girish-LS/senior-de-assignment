4. Step-by-step bronze execution flow

  1. Connect and create objects idempotently. The Databricks path creates schema bronze and four Delta tables if they do not already exist.
  2. Decide full vs incremental mode. Full load reads everything. Incremental mode reads the stored watermark and applies a 72-hour trailing lookback window.
  3. Fetch from the REST API. Both Databricks entrypoints use TransactionsApiClient.iter_transactions().
  4. Validate each record. Records either become typed Transaction objects or accumulate all validation failures.
  5. Flag duplicates. Duplicate detection hashes all business fields except transaction_id; the lowest transaction_id survives.
  6. Write quarantine rows. Failed records land in quarantine_transactions; a run clears its own quarantine rows first to stay idempotent within that run.
  7. Upsert bronze via MERGE. Valid records are staged and merged into bronze_transactions on transaction_id.
  8. Advance watermark only after success. The new watermark is the max valid transaction_date if it is higher than the previous value.
  9. Record metrics. Each run writes a metrics row capturing counts, timing, and watermark movement.

Watermark management

Why gte instead of gt? The API filter intentionally re-reads the boundary timestamp so records that share the exact watermark are not skipped forever.

effective_from = apply_lookback(watermark_before, 72)
# filter passed to the API: gte.<effective_from>

Why compute the watermark from valid records only? This dataset contains invalid records dated 2024-04-15 and 2024-11-31, later than every valid record. A raw-record watermark would jump to November and silently stop future ingestion.

Zero-record guard. Repository source files databricks/notebooks/01_ingest_bronze.py and scripts/ingest_to_databricks.py both raise instead of reporting success when an incremental Databricks run with a lookback window fetches zero rows, because that window should still contain the watermark-setting record. The guard exists specifically to catch malformed filters such as historical gte.gte.<timestamp>.

Validation and quarantine

  • Validation enforces strict UTC timestamp format, positive decimal amount, accepted enumerations, non-blank merchant names, and assigned ISO 3166-1 alpha-2 country codes.
  • Every failure reason is retained; validation does not stop at the first error.
  • Quarantine rows store the raw JSON record, a semicolon-separated error message, error count, and failed field list.
quarantine_id, transaction_id, raw_record, error_reason, error_count,
failed_fields, ingestion_timestamp, ingestion_run_id, source_system

Duplicate handling

  • Duplicates are flagged in bronze, not dropped at ingestion time.
  • The survivor is deterministic: the lowest transaction_id in each duplicate group.
  • Silver resolves the correctness choice by filtering is_duplicate = 0.
  • Committed evidence shows 5 duplicate groups under outputs/databricks/duplicate_groups.csv.

MERGE INTO upsert pattern

MERGE INTO workspace.bronze.bronze_transactions AS target
USING bronze_incoming AS source
   ON target.transaction_id = source.transaction_id
WHEN MATCHED     THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *

This is the Delta equivalent of the local SQLite INSERT ... ON CONFLICT pattern. It is the mechanism that makes the deliberate gte overlap safe.

5. dbt transformation path

Silver: stg_transactions

  • Materialized as a view.
  • Reads Databricks bronze as a dbt source whose schema is explicitly set to bronze.
  • Casts amount once at the silver boundary.
  • Creates transaction_day from the timestamp string.
  • Filters out duplicate rows with where is_duplicate = 0.
select *
from {{ source('raw', 'bronze_transactions') }}
where is_duplicate = 0

Gold: daily_account_summary

  • Materialized as incremental with delete+insert.
  • Unique key: [account_id, transaction_date].
  • Includes only status = 'completed' transactions.
  • Recomputes affected days using a lookback that matches ingestion.
  • Contract is enforced in schema.yml.
{{ config(
    materialized='incremental',
    unique_key=['account_id', 'transaction_date'],
    incremental_strategy='delete+insert'
) }}

The exact Databricks build command is:

cd dbt_project
dbt deps

7. Portability findings from the DuckDB-first dbt path to Databricks

FindingWhat worked locallyDatabricks outcome / resolution
timestamp with time zoneDuckDB contract accepted a timezone-aware timestamp type.Spark SQL does not expose that type in the same way. Resolved by normalizing the model output to plain timestamp.
VARCHAR in the dbt contract/cast pathDuckDB accepted the generated cast(null as varchar) shape used by the model contract.That specific Databricks/Spark path raised DATATYPE_MISSING_SIZE; the repo resolved it by declaring string, which Databricks accepts and DuckDB treats as an alias.
listagg order_byDuckDB honors ordering for the currencies list.Spark/Databricks ignores order_by_clause in dbt's listagg. This remains documented rather than hidden.
UTF-8 BOMDuckDB tolerated files that started with a BOM.Spark SQL parsing failed; the repo explicitly documents the issue and already handles BOMs in config file reading.

The broader conclusion is that dbt model contracts are expressed in the destination warehouse's type system. Cross-engine portability therefore requires explicit output normalization, not just SQL that “looks portable”.

8. Key design decisions

gte instead of gt: prevents permanent loss of records that share the exact watermark timestamp.

Watermark from valid rows only: avoids the invalid-date trap created by later-dated quarantined records.

Zero-record guard: catches malformed incremental filters rather than treating an impossible empty window as success.

Duplicates flagged in bronze, resolved in silver: keeps source-quality observability while making the correctness choice reversible downstream.

Bronze stores raw values as STRING: preserves source fidelity and keeps money out of floating-point representation before silver decides types.

Gold uses delete+insert, not merge: aggregate rows must be recomputed from all contributing records when late-arriving data lands.

10. Idempotency proof

Evidence from committed artefacts:

  • ingest_run1.json: watermark_after = 2024-03-30T21:01:36Z
  • ingest_run2.json: same watermark_before and watermark_after, with effective_filter_from = 2024-03-27T21:01:36Z
  • idempotency_check.txt: bronze row count remains 349 before and after the rerun
bronze rows before rerun : 349
bronze rows after rerun  : 349
result                   : PASS - zero new rows

Why the proof holds:

  1. The incremental filter deliberately re-reads a trailing window using gte.
  2. MERGE INTO matches on transaction_id and updates existing bronze rows instead of duplicating them.
  3. The watermark advances only after a successful write and only to the maximum valid transaction date.

The combination of those three choices makes incremental overlap safe, measurable, and repeatable.

11. Execution summary

The Databricks path is a medallion-style pipeline with two interchangeable ingestion entrypoints, a shared validation/deduplication core, Delta bronze control tables, dbt-modeled silver and gold layers, and a job definition that keeps ingestion and transformation independently retryable. The design choices around gte, valid-only watermarking, and Delta MERGE INTO are not isolated implementation details; together they are the idempotency strategy.
